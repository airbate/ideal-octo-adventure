# 嵌入式启动链：从复位向量到 main

跟踪启动文件、堆栈、C 运行时、链接脚本和 bootloader 跳转。这类问题不能只靠一条经验解决，关键是先把数据流、约束和验证方式说清楚，再选择实现策略。

## 先建立可验证的模型

工程实现应该从最小模型开始：明确输入输出、边界条件、资源限制和失败行为。对于并行程序，要同时记录线程映射、内存访问和同步点；对于芯片与嵌入式模块，则要把时钟、复位、接口协议以及异常路径写进规格。模型越清楚，后续仿真、波形检查和性能测量越容易复现。

## 再用实验缩小问题

不要一次修改很多变量。先准备一个小而确定的测试向量，使用日志、波形、计时器或分析器观察现象，再逐项改变实现。性能问题要区分计算、访存、调度和数据搬运；功能问题要区分索引、时序、并发和初始化。每次实验都保留版本、参数和结果，避免“修好了但不知道为什么”。

## 最后守住工程边界

一个可交付的实现必须说明支持的输入范围、精度或时序裕量、资源消耗和已知限制。将参考实现作为正确性基线，把回归测试、边界案例和错误处理纳入提交标准。这样得到的结论才能从一次 demo 变成可维护的工程知识。

这也是我在芯片、CUDA 和嵌入式开发中最看重的习惯：先把问题变得可测量，再让优化和抽象建立在证据之上。
